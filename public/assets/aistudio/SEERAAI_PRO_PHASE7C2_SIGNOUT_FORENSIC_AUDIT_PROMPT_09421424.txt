REQUIRED FORENSIC QUESTIONS — ANSWER EACH WITH EXACT CODE EVIDENCE
A. QUEUE AND LOCAL-ONLY DATA PROTECTION
1. Does logout inspect every relevant queue and every local-only draft store before deleting anything?
2. Does it distinguish (i) cloud-confirmed data, (ii) queued/unacknowledged writes, and (iii) local-only drafts?
3. Is there an actual server/Firestore acknowledgement for every pending write before its local copy is purged? Identify the awaited promise and success condition. A boolean such as clearCache=true or a user checkbox is NOT proof of sync.
4. If the network is unavailable, a write rejects, a timeout occurs, or the tab closes, are unsynced drafts preserved and is the user kept informed?
5. Can a broad localStorage prefix deletion remove queue entries or drafts before their sync state is confirmed?

B. IN-FLIGHT OPERATIONS AND RACE CONDITIONS
1. Does the logout flow acquire a real lock that prevents new writes and pauses background sync?
2. Does it await every in-flight sync/write operation, or safely cancel it with a documented recovery path?
3. Show the exact await chain from logout initiation through queue flush, acknowledgement, cache purge, Firebase signOut, and React state reset.
4. If Firebase signOut fails after local cache purge, what exact state results? Can the previous account remain authenticated while its local data has been deleted?
5. Does the implementation avoid a race between a queued write, a retry timer, a service worker, and sign-out?

C. INDEXEDDB DELETION SEMANTICS
1. Is indexedDB.deleteDatabase() awaited through its IDBOpenDBRequest events (onsuccess/onerror/onblocked), or is it merely called?
2. A synchronous try/catch does not catch asynchronous IDB request errors. Determine whether errors and blocked events are actually handled.
3. Are all database names and object stores enumerated from the actual code? Could deleting any database remove unrelated or still-unsynced information?
4. Does the application confirm deletion success before allowing another user/account to sign in?
5. What happens when another tab or an open database connection blocks deletion?

D. MULTI-TAB ISOLATION
1. window.dispatchEvent(new CustomEvent(...)) only notifies listeners in the same window. Is there an actual cross-tab mechanism (BroadcastChannel, storage event caused by another document, or SharedWorker/service worker coordination)?
2. Show the sender and receiver code, message payload, listener registration, and cleanup.
3. Test or explain whether tabs on the same origin but different accounts can see each other's cached data during account switching.
4. What happens if a tab is suspended, offline, or opened after the broadcast?

E. MODAL AND USER CONSENT
1. Inspect LogoutConfirmationModal and prove exactly what each checkbox/button does.
2. Is “Discard Unsynced Changes & Sign Out” a distinct, explicit action from ordinary sign-out?
3. Does the modal show the number/list/type of unsynced items and explain irreversible loss?
4. Can the modal accidentally select clearCache=true by default without meaningful consent?
5. Does cancellation truly leave the user signed in and preserve all local data?

F. ERROR HANDLING AND AUTH STATE
1. Do not label a purge as successful when IndexedDB deletion is blocked or fails.
2. Does a failure keep the user from switching to a different account on that browser profile until isolation is guaranteed?
3. Are user/profile/accessToken resets sequenced consistently with Firebase signOut and successful cleanup?
4. Are owner privileges and cached identity tokens removed only after the necessary checks, without breaking recovery of unsynced work?
