3. CRITICAL TELEGRAM COLLECTION ACCESS REVIEW
The Phase 8B.3.1 report says the following collections currently have broad rules equivalent to `allow read, write: if true;` at approximately lines 143–172:
- telegram_polls
- telegram_channels
- telegram_posts
- telegram_archive
- telegram_messages
- telegram_channel_feed
- telegram_subscribers
- telegram_user_stats
- telegram_poll_results
- telegram_briefing_logs

Treat this as a HIGH-PRIORITY security finding. Public read/write permits unauthenticated users to read, create, overwrite, or delete matching documents unless a more specific operation is independently constrained. Do not describe this as safe merely because the feature is called community archiving.

For EACH collection separately, determine from actual application code and data schema:
A. Is the collection intended to be publicly readable?
B. Does it contain only deliberately public information, or could it contain subscriber data, user identifiers, private messages, unpublished drafts, operational logs, moderation data, or court/legal records?
C. Which exact actor types may read/list/get/create/update/delete?
D. Which fields may the client set or change?
E. Which operations are server-only and must be protected from client writes?
F. Are there query constraints or document fields needed to enforce public visibility?

Produce a per-collection access matrix with separate permissions for get, list, create, update, and delete. Do not use a single broad `read, write` permission where distinct operations are required.

Proposed default design to evaluate against actual product behavior:
- Publicly released Telegram posts/feed/archive content may be public READ ONLY only when the record is explicitly marked/published as public and contains no private fields.
- Client writes must be denied by default unless the feature demonstrably requires them. Where writes are required, restrict them to authenticated, authorized roles and validate allowed fields, types, sizes, immutable ownership/channel IDs, and state transitions.
- Subscriber records, user stats, briefing logs, private messages, moderation records, and poll results must not be presumed public. Identify the actual fields and business requirements before deciding access.
- Poll submissions, if supported by clients, must be constrained to the authenticated user and valid poll/options; prevent arbitrary result manipulation, duplicate voting where applicable, and unauthorized deletion. Prefer trusted server-side writes for aggregate results when the architecture supports it.
- `telegram_legal_documents` public read is allowed only if the records are intentionally public legal resources. Inspect whether the collection can contain drafts, uploaded source files, restricted court content, or unverified legal material. If mixed, propose a publication/status model or segregated access paths; do not expose the entire collection indiscriminately.

4. FIRESTORE RULES OVERLAP REVIEW
Inspect EVERY matching rule for each Telegram collection and all broader parent/recursive matches, including `match /{document=**}`.
Remember that overlapping Firestore `allow` expressions are additive/OR: any matching allow expression that evaluates true grants access. A broad false rule does not cancel another matching true rule.
Produce a complete overlap table: request path, matching rules, each allow expression, resulting effective permission, and proposed remediation.
Review `isAdmin()` and every privileged helper. Identify hardcoded fallback email addresses. Do not reproduce actual addresses in the final report; identify the code location and risk.
The global recursive admin fallback grants broad administrator access across matched paths. Verify that admin status is established through trusted server-issued custom claims or another secure, auditable mechanism. Do not accept client-editable profile fields as proof of admin status.
Prepare a safe transition plan to retire hardcoded email fallbacks only after legitimate administrator claims are safely provisioned and verified. Do not change claims or remove the current access path in production.

5. STORAGE TENANT ISOLATION — REQUIRED REVIEW
The reported path is:
`/legal_docs/{institutionId}/{userId}/{allPaths=**}`
The Phase 8B.3.1 summary says owner access checks `request.auth.uid == userId`, while staff read checks a matching institutionId claim and staff role.
Determine whether owner read AND owner write ALSO require:
`request.auth.token.institutionId == institutionId`
If not, flag the missing tenant-boundary check. Do not assume UID ownership by itself proves access to every institution path.
Review all operations separately: get/download, list, create/upload, update/overwrite, delete, and metadata changes.
For every upload, validate allowed MIME types, maximum size, and any required metadata. Ensure a user cannot change institutionId, owner UID, or protected metadata through an overwrite/update. Verify all application upload paths exactly match the Rules paths.
Check other Storage paths used by the app; do not infer that `/legal_docs` is the only path.
Produce a path/actor/operation matrix and negative test cases for cross-institution access.
