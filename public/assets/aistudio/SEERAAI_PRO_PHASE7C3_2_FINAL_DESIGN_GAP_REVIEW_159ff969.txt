REQUIRED DESIGN GAPS TO RESOLVE

A. CORRECT CROSS-TAB ORDERING
The Phase 7C.3.1 design sends SESSION_TERMINATED after LOCAL_PURGE, while its receiver protocol expects other tabs to close IndexedDB connections before deletion. Correct this contradiction.
Specify a two-stage protocol, for example:
1. PREPARE_SIGN_OUT / CLOSE_DB_CONNECTIONS broadcast with UID, correlation ID, and database names.
2. Each matching-UID tab stops new writes and background sync, drains or safely pauses its work, closes all owned IDB connections, and returns an acknowledgement.
3. The initiating tab waits for acknowledgements with a bounded timeout and an explicit safe failure branch.
4. Only after connections are confirmed closed should it attempt database deletion.
5. Only after successful local cleanup and Auth outcome should it broadcast the final SESSION_TERMINATED event.
Define behavior for missing tabs, stale messages, duplicate messages, wrong UID, unavailable BroadcastChannel, suspended tabs, and acknowledgement timeout. Do not assume a message post means it was received.

B. INDEXEDDB DELETION LIFECYCLE
Review the proposed safeDeleteOfflineDB() wrapper. Correctly handle onsuccess, onerror, onblocked, timeout, and possible late success after a timeout. Explain that deleteDatabase() requests cannot be cancelled, and prevent overlapping retries while an earlier request may still be pending. Specify connection tracking and onversionchange handling in every module that opens the database. Do not report success for SSR/no-indexedDB paths unless the application has explicitly established that no browser-side data exists. A timeout or blocked state must remain a failure/unknown state, not success.

C. IN-FLIGHT WRITES AND QUEUE DRAINING
The proposed 3,000 ms drain timeout has no clearly defined branch. Define exactly what happens if pending writes cannot finish within the deadline. The safe default must preserve queued/local-only data and keep the current user session usable, or otherwise enter a controlled locked state that prevents account switching and cross-user access. Do not continue destructive cleanup after an unconfirmed drain. Define lock acquisition, blocking new writes, stopping background sync, awaiting already-started writes, resuming sync after cancellation, and releasing locks in finally paths.

D. DATA CLASSIFICATION AND CLOUD ACKNOWLEDGEMENT
Verify all actual stores/keys and the actual schema fields before proposing inventory. Distinguish:
- server-confirmed data;
- pending edits;
- local-only drafts;
- derived disposable caches;
- user preferences;
- authentication/session state;
- institutional/court data.
Do not use a timestamp or local boolean alone as proof of cloud persistence. Define authoritative acknowledgement using the actual Firebase SDK behavior, successful server-accepted write, document identity/revision, and any necessary server read/metadata check. Account for offline persistence and pending writes. Verify whether getQueuedEdits(), getSavedDocuments(), syncQueuedEdits(), STORE_EDITS, STORE_SYNC_QUEUE, STORE_INSTITUTIONS, and other names actually exist.

E. SHARED-DEVICE PRIVACY VS PRESERVING OFFLINE DRAFTS
The current proposal says unsynced/local-only drafts may be preserved after sign-out. That may expose plaintext data on a shared court/public terminal. Do not treat “preserve locally” as automatically safe.
Give explicit safe user choices and behavior:
- retry synchronization and remain signed in if it fails;
- cancel sign-out and preserve all data;
- explicitly discard selected unsynced/local-only items after showing exact counts and item identity (without exposing sensitive contents unnecessarily);
- alternatively, if preservation after sign-out is required, design a genuinely user-bound encrypted offline vault with a defensible key lifecycle and re-authentication/unlock process.
Do not claim encryption is secure without describing key derivation, storage, unlock, recovery, account change, and loss-of-key behavior. Plaintext local preservation must not permit the next user to read the prior user's drafts.

F. INSTITUTIONAL RECORDS AND RETENTION
Correct the assertion that STORE_INSTITUTIONS and audit logs should simply never be purged locally. Distinguish authoritative server records from disposable local replicas/caches. Local cache retention must follow confirmed institutional policy, least-privilege access, encryption, and device-management rules. Mark legal/institutional retention questions as unresolved if no actual authoritative policy text is available. Do not invent Ethiopian or Oromia retention requirements.

G. AUTH SIGN-OUT AND CLEANUP FAILURE ORDER
Analyze consequences if Firebase signOut(auth) fails after local credentials/cache have been cleared, and if it succeeds but local cleanup fails. Propose an idempotent, recoverable state machine. Define what is blocked on cleanup failure (especially account switching), how the app avoids presenting a false signed-out/safe state, and how the prior user can recover unsynced work. Avoid leaving stale auth tokens or privileged in-memory claims. Clearly separate local sign-out, remote token/session behavior, local data purge, and cross-tab confirmation.

H. BROADCAST MESSAGE SCHEMA AND SECURITY

Validate origin/channel scope, UID matching, correlation IDs, timestamps, and replay/duplicate handling. Do not include secrets or document contents in messages. Include ACK semantics and timeout handling. Explain fallback behavior when BroadcastChannel is unavailable; do not imply window.dispatchEvent is cross-tab.
