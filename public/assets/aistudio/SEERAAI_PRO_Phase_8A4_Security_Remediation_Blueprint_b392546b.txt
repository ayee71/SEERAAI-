3. PHASE 8A.3 FINDINGS TO VALIDATE

The previous read-only audit reported the following issues. Independently verify each finding against the actual workspace before accepting it.

A. Firestore Rules

The previous audit identified:

1. Potential public read/write permissions using "if true" in:

   - "institutions/{institutionId}/courtDocuments"
   - "institutions/{institutionId}/auditLogs"
   - "witness_schedules"
   - Ten "telegram_*" collections
   - Other analytics, feedback, discussion, and court-related collections.

2. Broad permissions based only on "isSignedIn()", potentially allowing any authenticated account, including anonymous authentication accounts, to access resources without sufficient role or institution checks.

3. Potentially undefined helper functions:

   - "signedIn()"
   - "isCourtReporterOrStaff()"

4. Admin authorization based on email allowlists without consistently requiring verified email status.

5. User profile updates that may permit modification of privileged fields, including:

   - "role"
   - "subscriptionTier"
   - "courtId"
   - "uid"

6. A global wildcard rule:
   "match /{document=**}"

7. Missing or inconsistent tenant isolation across court collections and subcollections.

IMPORTANT: Analyze overlapping Firestore match statements correctly. Firestore allow expressions from matching rules are additive (OR logic). A restrictive rule does not cancel a permissive matching rule. Explain precisely which users can access each affected resource. Do not incorrectly claim that a global admin-only rule makes a collection public by itself.

B. Firebase Storage Rules

The previous audit identified:

1. Storage rules appear to allow uploads under:
   "legal_docs/{institutionId}/{userId}/{allPaths=**}"

2. Other application services reportedly upload to:
   "institutions/{institutionId}/courtDocuments/..."

3. Court logo uploads reportedly use:
   "court_logos/{institutionId}/..."

4. The Storage owner rule may check the UID but fail to verify that the user's institution ID matches the requested institution path.

5. Some application roles may be excluded from institutional document access.

6. Existing upload services may use synthetic user identifiers or fallback paths that do not match Firebase Authentication UIDs.

7. A fallback mechanism may store document contents as base64 data URLs inside Firestore when Storage uploads fail.

Verify all these findings against the actual implementation.

C. Tenant Isolation

The previous audit reported:

1. Missing "institutionId" validation in some court services.
2. Court case records and related subcollections may lack consistent institution ownership.
3. Some court collections may not have explicit tenant-specific match rules.
4. Custom claims such as "institutionId", "role", "courtRole", and "admin" may be required by rules.
5. No "setCustomUserClaims" implementation was found in the previously inspected repository.
6. Firebase Admin SDK operations bypass Firebase Security Rules and therefore require authorization and tenant checks in backend code.

Verify the actual situation and distinguish source-code evidence from live Firebase state.

5. DESIGN THE TARGET SECURITY ARCHITECTURE

Prepare a proposed security architecture that addresses the following requirements.

A. Firestore authorization

Design rules that enforce:

- Deny-by-default access.
- Authenticated user checks.
- Verified email requirements where appropriate.
- Role-based authorization.
- Institution-based tenant isolation.
- Document ownership and access controls.
- Separate permissions for judges, assistant judges, registrars, court staff, auditors, and legal experts.
- Proper administrator authorization.
- Immutable protected user fields.
- Restricted access to audit logs.
- Restricted access to witness identities and schedules.
- Restricted access to evidence, audio recordings, and court documents.
- Safe handling of Telegram legal-source collections.
- Proper validation of document creation, modification, and deletion.

Do not assume that being signed in automatically grants access to court records.

B. Storage authorization

Design one consistent Storage path convention that works with the existing application.

The design must ensure:

- Institution ID is checked against authenticated claims or trusted authorization data.
- Owner UID is checked correctly.
- Authorized institutional roles can access permitted court documents.
- Unauthorized users cannot access another institution's documents.
- Upload, read, update, and delete permissions are separated.
- File size and content type are validated.
- Sensitive documents are not stored in publicly readable Firestore fields as an upload fallback.
- Existing document references and metadata remain recoverable.

Do not propose deleting existing files or changing their paths without a verified migration and backward-compatibility plan.
