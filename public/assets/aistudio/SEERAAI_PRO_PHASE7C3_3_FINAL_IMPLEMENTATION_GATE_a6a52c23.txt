CRITICAL DESIGN GAPS TO RESOLVE
1. SIGN-OUT / PURGE / FIREBASE ORDERING
The Phase 7C.3.2 state machine currently places Firebase sign-out before IndexedDB purge. Analyze failure cases:
- Firebase signOut succeeds but IndexedDB purge fails or remains blocked.
- IndexedDB purge succeeds but Firebase signOut fails.
- Browser closes or crashes between stages.
- A stale authenticated tab continues to write or sync.
Propose a single explicit sequence that preserves pending data while preventing the next user from accessing the prior user's plaintext data. Define precisely what the application does on every failure. Never label a failed or incomplete purge as success.

2. UNSYNCED AND LOCAL-ONLY DATA ON SHARED DEVICES
Inventory actual data stores and distinguish:
- server-confirmed records;
- queued edits awaiting server acknowledgement;
- local-only drafts never uploaded;
- disposable derived caches;
- institutional/court-record replicas;
- non-sensitive preferences.
Explain the unavoidable trade-off: preserving plaintext local-only drafts after logout can expose them to the next user, while deleting them can cause data loss. Specify safe user choices and default behavior. Do not assume a draft is cloud-confirmed based only on a timestamp or local flag. Define verifiable server acknowledgement (server-committed write, authenticated owner, stable document ID, revision/version or content hash, and any necessary server read-back). If safe retention requires encryption or a secure export, specify the key lifecycle, recovery path, and how another account is prevented from decrypting it. If this cannot be implemented safely with current architecture, say so and keep that flow NO-GO.

3. INDEXEDDB LIFECYCLE
Inspect every code path that opens SeeraAIOfflineDB and every connection owner, including background sync, workers, and service workers if present.
Specify:
- onversionchange handlers that close connections;
- cross-tab request/ack protocol for closing connections;
- behavior when a tab is suspended, crashed, unresponsive, or fails to ACK;
- deleteDatabase onsuccess/onerror/onblocked handling;
- timeout semantics.
Important: onblocked is not success. deleteDatabase requests cannot be cancelled. Do not launch a second deletion request while the first request is still pending. If a timeout occurs without a terminal request event, report an unresolved deletion and fail closed; do not claim the database is removed and do not permit another account to use the profile until isolation is verified.

4. REAL CROSS-TAB COORDINATION
A BroadcastChannel send alone does not prove all tabs received or completed the request. Define message fields including uid, correlationId, senderTabId, recipientTabId where relevant, message type, and timestamp. Explain how active tabs are discovered/registered, how ACKs are correlated, how duplicate/stale messages are ignored, and what happens if any tab does not ACK. Do not treat a timeout as permission to assume success. Inspect whether the existing app already has a tab registry or only a document-sync channel.

5. BACKGROUND-SYNC AND WRITE LOCK
Identify exact methods that enqueue writes, start/stop polling, process queued edits, and expose in-flight promises. A mutex only inside AuthContext is insufficient if storage/backgroundSync modules can still write. Specify the shared lock contract and how every write path respects it. Define bounded drain behavior without silently discarding jobs.

6. INSTITUTIONAL COURT DATA / RETENTION
Separate canonical server-side court records from local replicas/caches. “Do not delete the official server record” must not mean “retain plaintext court data on a shared browser after logout.” Specify tenant/role isolation and local-cache handling. Flag any retention/legal-policy question that must be decided by the competent judicial administrator; do not invent Ethiopian retention rules.
