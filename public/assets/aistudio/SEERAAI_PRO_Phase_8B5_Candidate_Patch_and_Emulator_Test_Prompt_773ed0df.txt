3. DESIGN TELEGRAM RULES SAFELY
For public feed content, consider public READ ONLY for the minimum collections actually intended for public viewing. Require an explicit publication state/field grounded in the real schema (for example, published status), and prevent public users from reading drafts, queued posts, private messages, subscriber information, statistics, or logs.

Important query constraint: Firestore rules are not filters. If a collection rule permits reads only for documents with a publication condition, client queries must include compatible constraints so every possible returned document satisfies the rule. Identify and propose the exact query changes if needed; do not silently assume queries will work.

No client should receive unrestricted public create/update/delete access. Prefer server-side Admin SDK writes for Telegram ingestion, webhook processing, archive synchronization, poll result aggregation, subscriber/statistics processing, and administrative publication workflows when the existing architecture supports it. Admin SDK bypasses Firestore Security Rules; therefore every privileged backend route/job must independently verify Firebase identity, authorization, tenant scope where applicable, input validation, and audit logging. Do not describe Firestore Rules as authorizing Admin SDK calls.

If legalContentManager is retained for a workflow, decide whether the role should call a protected backend endpoint or directly write via client SDK. Prefer the backend endpoint for privileged publication and audit-sensitive changes. Any proposed direct client write must be separately justified, narrowly scoped by operation and field, and protected against users setting their own published/admin/tenant fields.

4. STORAGE TENANT-BOUNDARY DESIGN
Audit the actual path:
/legal_docs/{institutionId}/{userId}/{allPaths=**}

Verify proposed checks separately for read, create, update, and delete:
- request.auth exists and is not anonymous where required;
- request.auth.uid equals the path userId for owner operations;
- request.auth.token.institutionId equals the path institutionId for institution-scoped owner operations;
- institutional staff access requires both a permitted canonical role and matching institutionId;
- global admin behavior is explicit and minimal;
- no institutionId, owner UID, or role can be selected/changed by an untrusted client;
- contentType and size validations match existing supported file types and limits;
- updates cannot bypass validation;
- delete behavior is tested with correct Storage Rules semantics.

Do not automatically block legitimate personal documents if the source shows a supported non-institutional path. Classify those paths separately and preserve intended functionality with least privilege.

Add or update tests covering at minimum:
TELEGRAM
- unauthenticated public read of approved published public feed documents: allowed only where intended;
- public read of draft/unpublished/private documents: denied;
- public create/update/delete in every Telegram collection: denied;
- ordinary authenticated user write: denied;
- legalContentManager allowed only through the specifically approved route or narrowly scoped operation;
- unauthorized user cannot set publication flags or change author/tenant fields;
- subscribers, user stats, private messages, poll results, and briefing logs: access denied to public and ordinary users;

STORAGE
- owner in matching institution can perform only intended operations;
- owner UID with mismatched institutionId is denied;
- another user's UID is denied;
- staff role in matching institution gets only intended read access;
- staff role in another institution is denied;
- untrusted user cannot upload to another institution's path;
- unauthorized update/delete is denied;
- invalid MIME type and oversized file are denied;
- valid supported file and size are allowed;
- anonymous/no-claim/missing-role cases fail closed.

OVERLAP / FALLBACK
- prove the global catch-all cannot re-open a denied path;
- prove no other matching allow statement grants the same caller access;
- enumerate all matching match blocks for each sensitive path.

Record exact command lines, emulator startup output, test file names, total/passed/failed/skipped counts, and relevant logs. Do not manufacture passing results or reduce tests to make the report look successful.
