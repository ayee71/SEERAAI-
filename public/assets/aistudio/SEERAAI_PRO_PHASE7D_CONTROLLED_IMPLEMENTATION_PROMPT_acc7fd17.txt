IMPLEMENTATION REQUIREMENTS
A. Sign-out lock and sync lifecycle
- Implement a per-session sign-out state/lock that prevents new local edits and queue additions once sign-out begins.
- Pause background polling and service-worker sync triggers using the existing architecture. Do not destroy unrelated listeners or permanently disable sync.
- Track and await actual in-flight writes/sync tasks. A timeout must produce an explicit safe-hold result, never be interpreted as successful synchronization.
- Inventory ALL relevant stores before any purge. Distinguish, at minimum:
  1) server-confirmed records;
  2) queued/pending edits;
  3) local-only drafts/annotations;
  4) disposable derived caches;
  5) non-sensitive preferences;
  6) local copies of institutional/court records.
- Treat a record as cloud-confirmed only with a successful server acknowledgement tied to the correct user, document ID, and revision/version. A local timestamp, optimistic UI update, queue removal, or client-side flag alone is not proof.
- Do not silently discard pending or local-only work. Offer Retry Sync, Stay Signed In, and an explicit destructive discard choice with a second clear confirmation. Default destructive consent to false.
- If a user declines discard and sync cannot complete, keep the same user signed in and block account switching. Do not leave the app in a state where another user can access the previous user's plaintext drafts.
- Do not invent an encryption scheme or claim offline drafts are safely retained after sign-out unless the existing code actually provides and tests user-specific encryption. If no safe encrypted recovery/export mechanism exists, disclose this limitation and use the safe-hold behavior.

B. IndexedDB lifecycle
- Implement an awaited deletion helper using the actual database names found in source.
- Handle onsuccess, onerror, onblocked, and a bounded timeout. `onblocked`, timeout, or an exception is NOT success.
- Register `db.onversionchange` on every relevant database connection so the connection closes promptly when deletion is requested. Find and update every actual connection-opening location needed for this guarantee.
- A BroadcastChannel message requesting connections to close is advisory; do not assume it closed a connection without an acknowledgement or an actual successful delete result.
- If deletion remains blocked or fails, enter an explicit isolation/lockdown state and prevent another account from logging into that browser profile until isolation is verified. Do not report sign-out cleanup as complete.
- Never delete an entire database if it contains user data that has not been safely synced or explicitly discarded. If selective object-store/record cleanup is safer and consistent with the existing schema, prefer it; explain the choice.

C. Cross-tab coordination
- Use the existing browser messaging architecture where possible; do not create competing channels unnecessarily.
- Implement a two-stage protocol with a unique correlation ID and the current UID: PREPARE_SIGN_OUT, tab acknowledgements, then SESSION_TERMINATED only after the initiating flow reaches the appropriate confirmed state.
- Each receiving tab must verify the UID, stop writes/sync, close its IndexedDB connections, clear in-memory sensitive state, and acknowledge preparation. Ignore messages for another UID or stale correlation ID.
- A missing acknowledgement is a failure/unknown state, not success. The initiating tab may request database closure and attempt deletion, but must not allow account switching or claim full isolation unless deletion and auth-state checks succeed.
- Do not rely on window.dispatchEvent for cross-tab communication.

D. Firebase Auth ordering and failure handling
- Coordinate Firebase sign-out with local purge so neither a stale authenticated session nor a previous user's plaintext cache can be exposed to the next account.
- After calling signOut(auth), verify the actual auth observer/current-user state before reporting signed-out completion.
- If Firebase sign-out fails or auth state remains authenticated, do not claim success and do not permit another account to sign in. Enter a clear safe-hold/lockdown result and preserve diagnostic information without logging secrets.
- If local purge fails after Firebase sign-out, keep the app locked against account switching and report cleanup incomplete. Do not treat a redirect alone as proof that storage was purged.
- Never clear institutional canonical records on Firestore/Storage. Distinguish those server records from their local replicas. Local replicas of sensitive institutional records must follow the applicable institutional policy and must not remain readable to a subsequent user on a shared device. If the retention policy is unknown or a proposed action could affect official records, stop that specific operation and report the policy dependency.
