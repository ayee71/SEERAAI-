REQUIRED DESIGN AREAS

A. DATA INVENTORY AND AUTHORITATIVE QUEUE DISCOVERY
1. Trace all sources of offline/local data across storage.ts, backgroundSync.ts, indexedDb.ts, precedentOfflineSync.ts, AuthContext.tsx, modal components, and any other actual callers.
2. Identify every localStorage key, IndexedDB database, object store, in-memory queue, pending write, retry queue, and local-only draft relevant to sign-out.
3. Distinguish at least:
   - Cloud-confirmed records (with a concrete acknowledgement/sync marker, not assumption),
   - Pending/queued edits,
   - Local-only drafts not yet uploaded,
   - Downloaded/cache-only copies,
   - Non-sensitive preferences.
4. Identify the real queue APIs and whether getQueuedEdits() includes every object store and localStorage queue. Do not assume a single queue is authoritative.
5. Explain how records are correlated to the active Firebase uid and institutionId, and how stale data from a prior user is isolated.
6. Define behavior for corrupt, unreadable, partially migrated, or unknown-version offline data. Default must be preservation and blocking destructive purge, not silent deletion.

B. SAFE SIGN-OUT STATE MACHINE
Design explicit states, for example:
IDLE -> LOCKING_WRITES -> PAUSING_SYNC -> DRAINING_IN_FLIGHT_WRITES -> INVENTORY -> SYNC_OR_PROMPT -> AUTH_SIGN_OUT -> LOCAL_PURGE -> VERIFY_PURGE -> COMPLETE.
Failure states must include CANCELLED, SYNC_FAILED, PURGE_BLOCKED, PURGE_FAILED, AUTH_SIGNOUT_FAILED, and RECOVERY_REQUIRED.
For each state specify entry conditions, awaited operations, timeout policy, retry behavior, user-visible message, and whether the user remains signed in.

Important safety rules:
1. Acquire a per-user/per-tab lock that prevents new local writes and new background-sync scheduling during sign-out. Avoid deadlocks and stale locks; specify lease/timeout/recovery behavior.
2. Pause background sync and await or safely cancel every in-flight write. A local function return or request dispatch is not proof of Firestore commit.
3. Only mark an item cloud-confirmed after the actual relevant Firestore/Storage operation succeeds and the application records a durable acknowledgement.
4. When pending/local-only items exist, show counts and safe choices. Recommended choices: Retry Sync; Stay Signed In; or Discard Unsynced Data & Sign Out with a separate, explicit, item-count-aware confirmation. Do not preselect destructive discard.
5. If the user cancels, preserve all data and restore normal sync/write operation.
6. If sync fails or network is unavailable, preserve pending/local-only data and keep the user signed in unless the user explicitly confirms discard after seeing what will be lost.
7. Do not equate Firebase signOut success with Firestore write acknowledgement.
8. Decide and document the ordering of auth sign-out and cache deletion so that neither a failed purge nor a failed auth sign-out leaves another user able to see the prior user's data. Include a safe failure/recovery path.

C. INDEXEDDB DELETION LIFECYCLE
1. Design an awaited Promise wrapper for indexedDB.deleteDatabase() that handles onsuccess, onerror, and onblocked, with bounded timeout and clear terminal states.
2. Explain that onblocked is not success. Do not resolve the deletion Promise on onblocked. Define a connection-close protocol using db.onversionchange in every app-owned open connection and close workers/other owners where applicable.
3. Specify how the application enumerates actual database names safely; do not delete guessed or unrelated databases. Preserve only verified SEERAAI-owned database names.
4. Verify deletion after request success using a safe read-only existence/open check where technically valid. Avoid accidentally recreating a database while verifying absence.
5. If a database remains blocked or deletion errors, specify how sign-out fails safely and how the user is prevented from switching to another account in that same browser context until isolation is guaranteed.
6. Include browser compatibility considerations and avoid assuming indexedDB.databases() is universally available.

D. TRUE CROSS-TAB / WORKER COORDINATION
1. Design a BroadcastChannel protocol with versioned messages, tab/session identifiers, active uid binding (never include tokens/secrets), correlation IDs, acknowledgements, and timeout handling.
2. Include the storage event fallback if BroadcastChannel is unavailable; remember storage events do not fire in the same tab that writes the key.
3. All tabs must stop writes/sync for the old identity, close IndexedDB connections, clear in-memory sensitive state, and acknowledge completion.
4. Do not let a tab clear pending data merely because another tab requested logout. Define how unsynced data across all tabs is inventoried and reconciled before purge.
5. Include Service Worker/Web Worker participation if the repository actually uses them. Do not claim same-window CustomEvents provide cross-tab coordination.
6. Define behavior when a tab is suspended, crashes, is offline, or does not acknowledge. Fail closed for account switching if old-user data may remain visible.

H. TEST PLAN WITH REAL TEST NAMES AND ACCEPTANCE CRITERIA
Design tests, and clearly mark them PROPOSED until actually run:
1. No pending items: sign-out completes and only intended SEERAAI data is purged.
2. Pending localStorage queue: sign-out cannot silently delete it.
3. Pending IndexedDB queue and local-only draft: both are preserved on cancel/failure.
4. Successful final sync: only acknowledged records become purge-eligible.
5. Network loss during upload: user remains signed in and pending edits remain recoverable.
6. Write starts during sign-out: lock prevents new writes; in-flight write is awaited/cancelled safely.
7. IDB onsuccess: deletion completion is awaited and verified.
8. IDB onblocked: not treated as success; close connections and retry or fail closed.
9. IDB onerror/timeout: no silent purge success; no unsafe account switch.
10. Two tabs for same uid: coordinated stop/cleanup and acknowledgement.
11. Two tabs with one suspended/unresponsive: timeout and safe failure.
12. Account A signs out, Account B signs in: no access to A's drafts/cache/roles/institution state.
13. BroadcastChannel unavailable: storage-event fallback behaves safely.
14. Firebase signOut failure and local purge failure permutations: recoverable, non-leaking behavior.
15. Non-sensitive language/theme preferences remain intact.
16. Shared terminal / browser restart behavior.
For each test include fixture setup, exact command/test file if it exists, expected result, evidence needed, and whether it has actually been executed. Do not invent existing test names or claim tests were run.
