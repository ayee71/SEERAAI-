5. REQUIRED AUTHORIZATION MODEL ANALYSIS
============================================================
Recommend a coherent target model without implementing it.

A. Firebase identity:
- Verify Firebase ID token on the server using the trusted Admin SDK verification path.
- Reject missing, malformed, expired, revoked (where appropriate), or invalid tokens before reading privileged request-body fields or touching protected data.
- Do not trust req.body.uploaderRole, reviewerRole, uploaderEmail, institutionId, role, or owner identifiers as authorization facts.
- Do not trust localStorage, app state, email text from the request body, or passcode success alone as proof of Firebase identity.

B. Role and institution provisioning:
- Design a server-only, least-privilege custom-claims provisioning workflow if custom claims are the approved design.
- Specify which trusted administrative actor may grant, change, suspend, or revoke a role and institutionId.
- Specify verification of the target Firebase UID, employment/staff record, institution assignment, approval evidence, audit logging, and revocation.
- State how refreshed ID tokens receive changed claims and how sessions with stale claims are handled.
- A user must never be able to grant themselves admin, judge, registrar, auditor, legalContentManager, court_admin, or another privileged role.
- Do not implement setCustomUserClaims in this phase.
- If staff passcode accounts are not Firebase Auth users, propose a secure migration/identity-linking plan. Do not treat a generated cuser_* Firestore ID as a Firebase UID unless source proves it is one.
- Do not store plaintext passcodes/access codes. Determine whether they are stored plaintext, hashed, salted, rate-limited, rotated, or exposed; report exact evidence and a safe migration recommendation.

C. Institutional scoping:
- Every privileged court read/write must bind the authenticated UID to a server-controlled role and one authorized institution (or a formally approved multi-institution scope).
- Institution IDs supplied by a client must be compared against verified identity/authorization records; never accept arbitrary client-selected institution IDs.
- Prevent cross-institution access even for reads, audio, evidence extraction, deadlines, notifications, and audit logs.
- Separate public legal sources from confidential user documents and institutional court records.

D. Admin SDK access:
- For every Admin SDK route, enforce authorization in server middleware/service logic because Firestore Rules do not apply to Admin SDK server libraries.
- Define route-specific permissions, ownership checks, institution scope, allowed fields, validation, rate limits, audit logs, and error behavior.
- Avoid a global “any authenticated user” rule for privileged Admin SDK endpoints.
- Confirm least-privilege Google Cloud IAM/service account scope separately; IAM is not a substitute for end-user authorization.

E. Special privileged actions:
- Legal source upload: only an approved uploader/curator role can upload; server binds uploader UID and timestamp.
- Legal source review/publish: a distinct approved reviewer permission; uploader must not self-approve unless formally permitted.
- Court audio: authorized staff within the case institution only; access and changes logged.
- Deadline scan: scheduler/service identity or tightly authorized role only; bounded scope and abuse controls.
- Evidence metadata extraction: caller must prove access to the exact case/document and matching institution before Admin SDK writes.
- Admin endpoint: define whether “admin” is global or institution-scoped; do not assume a global super-admin grant is acceptable.
