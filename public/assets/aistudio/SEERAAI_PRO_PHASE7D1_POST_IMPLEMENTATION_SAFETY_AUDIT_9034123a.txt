A. IndexedDB deletion result handling
- Does logout inspect the returned { success, reason } from every safeDeleteOfflineDB() call?

- Does onblocked trigger a coordinated close/ack/retry path, or merely log and wait?

B. BroadcastChannel coordination
- Does PREPARE_SIGN_OUT have actual receiving listeners in all relevant tabs/workers?
- Does the initiating tab collect and validate ACK_PREPARE messages matching UID, correlationId, and tabId before proceeding?
- Is a timeout treated as missing acknowledgement rather than successful preparation?
- Does the code prevent account switching if any sensitive tab remains unresponsive?
- Does SESSION_TERMINATED cause all receiving tabs to halt writes/sync, clear in-memory auth state, and prevent stale authenticated UI?
- Are channel lifetime, listener cleanup, duplicate messages, stale messages, and UID mismatch handled?
- Does the implementation coordinate IndexedDB CLOSE_IDB messages and wait for actual connection closure?
C. Offline queue and local-only data
- Does logout enumerate the real IndexedDB stores and localStorage queue keys from source, rather than relying on guessed names?

- Is each cloud-confirmed record backed by a successful server acknowledgement and matching user/document/revision identifier? A timestamp alone is not sufficient.
- Is in-flight work actually awaited? A fixed timeout alone must not mark writes as synced.
- If sync fails or the network disconnects, are unsynced drafts preserved without exposing them to the next user?
- Is there an implemented encrypted user-specific recovery/export mechanism? If not, explain the shared-device privacy dilemma and do not claim it is solved.
- Does clearCache=false leave plaintext private records accessible to a subsequent user on a shared browser profile? Trace actual retrieval and user-scoping behavior.
D. Firebase Auth ordering and failure cases

- Does the application distinguish Firebase sign-out success from local cleanup success?
- Can it report logout completed when Firebase auth remains active?
- Can local drafts be deleted before a failed signOut leaves the user authenticated?
- Are Firebase auth persistence keys manipulated directly in a way that conflicts with the SDK?
- Is there a safe, tested recovery state for each partial-failure combination?
